Data Dictionary: making a model discoverable

Parts 1 and 2 were about what you build on a Malloy model and where people go to consume it. This part is about the model itself: can a person, or an agent, open a package they've never seen and work out what it knows, what it means, and what it can't answer? I prototyped two Console pages to explore that: a Data Dictionary that writes itself from any package, and a Question Coverage loop that scores the model against the questions people actually ask.

Noah Mac · product + design engineering update · Oct 4 - Oct 9, 2026
TL;DR
  • A data dictionary with zero configuration. Every source, measure, dimension, view, join, given and named query in a package gets its own page, built only from what Publisher already serves: model metadata, source text, compiled queries, and the package's dashboards, notebooks and data apps. Each page has live data, a content graph, and an Ask about this button.
  • The model documents itself, with a person in the loop. One click has Opus draft a #(doc) for every undocumented entity. You review, edit and accept each draft, and the Console turns the accepted ones into a model patch that is compile-checked against the package before anything is written. On storefront, that's 25 descriptions across two files, and documentation coverage goes from 62% to 100%.
  • A coverage score for "is this model good enough for AI?" Opus writes a set of realistic stakeholder questions, including ones the model probably can't answer. An agent with Publisher's own MCP tools and skills then tries to answer each one and gives a verdict: answerable, partly answerable, or missing. The verdicts roll up into a score, a heat map by theme, and a backlog of missing concepts.
  • Every gap becomes a handoff. Each verdict carries the agent's work, recommended model changes, and exit criteria, and downloads as a markdown brief for a coding agent. Re-scoring the same questions after a model change shows whether the number moved.
  • It's a prototype. Drafts and runs live in localStorage, there's no endpoint that writes a model file yet, and my OpenRouter balance ran out partway through the first coverage run. Both runs are below: the half-judged one that read 83, Good, and the complete re-score of the same questions, which reads 62, Fair.

01Why a dictionary

A semantic model is only as useful as its discoverability. If nobody can find the measure, nobody uses it, and an agent that can't find it will invent one.

Both earlier parts kept running into the same wall from different directions. In Part 1, the Explorer assumed you already knew the model's vocabulary, and labels lost their meaning once a field was reached through a join. In Part 2, the Library could list every dashboard in a package, but not explain the definitions underneath them. Meanwhile the agent path, get_context, ranks entities by their names and #(doc) text, so an undocumented column is close to invisible to it.

So I started from a one-page brainstorm of "views of the semantic model itself", with one rule: zero configuration, any package. Every tile has to light up on a package it has never seen, using only what Publisher already serves. Two ideas from that list became this prototype:

Idea What it is Route
Data Dictionary A browsable wiki of the model, one page per entity, with live data, related content, and AI-drafted descriptions for whatever is undocumented /:env/:pkg/dictionary
Question Coverage Generated business questions, each judged answerable, partly answerable or missing, rolled up into a score and a gap backlog /:env/:pkg/coverage

Everything below uses the bundled storefront package: six sources, 11 measures, 25 dimensions, 20 views and three joins over local DuckDB data. It's a small model, and well-documented for an example: 62% of its entities had a #(doc) before I started.

02The dictionary, on any package

Open a package and the dictionary is already there. Nobody has to write it, configure it, or keep it in sync.

The left rail is the model as a tree: sources, then their measures, dimensions, joins and views, then givens, named queries, and content. A dot beside each entity says whether it's documented (solid green), has a draft waiting (dashed), or has nothing (hollow). / focuses a search that ranks entities by name, label and doc text, and also matches content titles.

What it reads

The dictionary builds an in-browser ontology of the package from the same REST endpoints any client can use:

  • GET …/models/{path} for every model: the compiled model definition (fields, joins, primary keys, table paths, annotations), its sourceText, and its givens. Source locations let every page link to the exact line that defines it.
  • The package's dashboards, notebooks and data apps, with their text, so it can tell which content reads which source, view, or field.
  • POST …/models/{path}/query for the live data on each page, tagged with queryMetadata: {surface: "data-dictionary"} so those queries can be told apart from real usage later.

No server change was needed for any of the read side. The AI parts (drafting, chat, coverage) go through a small Cloudflare Worker, packages/console-ai, which the Vite dev server proxies at /ai/*.

03A page for every name

Every entity gets a page, and every page answers the same three questions: what is this, what does the data look like right now, and what else touches it?

That last distinction matters for discoverability. Most links are read from structure (imports, joins, tile queries, the model paths in a data app's HTML), and a few are textual mentions. The dictionary keeps them visibly separate rather than mixing confident links with guesses. An earlier version showed "Nothing in the model references this" on far too many pages, and the fix was to look harder for real links, not to infer them from names.

Ask about this

The chat runs on TanStack AI in the Worker, and it gets exactly what any external MCP client gets: every tool Publisher registers (get_context, execute_query, compile_model and the rest), plus the bundled skills, served as MCP prompts behind a load_skill tool, with malloy-analysis preloaded. Threads are titled automatically and kept in a history dropdown. Every question asked here is also filed into the package's Question Coverage (section 06).

04Describe the model: draft, review, promote

An undocumented field is a discoverability bug. The dictionary drafts the missing descriptions, and a person decides which ones become part of the model.

DraftOpus writes a #(doc) for every undocumented entity
→
ReviewEdit, accept, or discard each one, in the panel or on its page
→
PromoteAccepted drafts become a diff to the model files
→
CheckEach changed file is compiled by the package's own compiler
→
WriteToday: copy or download the patch. Later: write and reload

1 · Draft

On storefront, the undocumented entities are the 20 raw table columns behind customers, products, regions and order_items, plus the five views of the dashboard's overview source. Draft 25 missing sends them to Opus in batches of 12, three batches at a time, sources first and each followed by its own fields, so the panel fills in source by source. Each entity goes with its kind, type, formula, and up to eight neighbours it uses or is used by, with their docs.

The drafting prompt is deliberately modest: "Describe only what the name, type, formula and neighbours support; where meaning is uncertain, say what it appears to be rather than guessing a business rule." That shows up in the drafts. signup_date became "Date the customer appears to have signed up or created their account." A hedge is the honest answer when the only evidence is a column name, and it's exactly the kind of sentence a reviewer should either confirm or correct.

2 · Review

3 · Promote and check

Most of the work in promotion is deciding where a description can go. A measure, view or computed dimension gets a #(doc) line above its own definition. A raw table column has no definition to annotate, so the promotion rewrites the source's header into an include block, which needs Malloy's access_modifiers experiment turned on in that file:

##! experimental.access_modifiers  // added once per file
source: products is duckdb.table('data/products.parquet') include {
  #(doc) Cost of the product to the business, used to compute gross margin.
  `cost`
  #(doc) List price of the product in USD, before any discount; what an order line actually charged is order_items.sale_price.
  `retail_price`
  …
  *
} extend {
  primary_key: product_id
  …

When a description can't be written in place, the draft says why instead of failing silently: the entity is defined in a file this package doesn't publish, its definition moved since the dictionary read the model, the source already has an include block, or its declaration spans several lines (a SQL source, say), so there is no single header line to rewrite.

Why "Coming soon". Publisher has no endpoint that writes a model file. The dashboard and notebook PUT routes write files under dashboards/ and notebooks/ (compile first, hash-checked, rolled back on failure), and Part 2's data-app route does the same under public/apps/. A model write with the same rules is the missing piece. Until then, the patch is written for git apply or for a coding agent to apply. (macOS's BSD patch rejects it; git apply accepts it as is.)

05Question coverage: a score that moves

Documentation coverage says whether every field is described. Question coverage asks the more useful question: how much of what people want to know can this model actually answer?

Writing the questions

Each question comes back typed: its text, who asks it (a persona), a theme, and the two to five concepts a model needs to answer it. Concepts are typed the same way get_context search targets are (measure, dimension, source, view, dimensional_value), so a question can be checked against retrieval concept by concept.

The prompt asks for questions a real stakeholder would ask whether or not the model can answer them: some the model should cover, some at its edges, and some that need data it plausibly lacks (costs, targets, marketing, inventory, sentiment, forecasts). A coverage score built only from questions the model can answer would be flattering and useless. Here's a sample of the 25 Opus wrote for storefront, with how each landed in the first run and in the re-score:

Theme Persona Question First run Re-score
Revenue CFO What was our total revenue last month? answerable answerable
Regional Performance VP of Sales How does average order value in the West compare to the Northeast? answerable answerable
Products Merchandiser What are our top 10 products by units sold? partial, missing products answerable
Profitability Merchandiser Which products have the lowest markup between cost and retail price? partial, missing markup partial, missing products
Customers Growth lead How many new customers placed their first order each month this year? check failed partial, missing new customer count
Retention — What share of customers acquired last January have placed a repeat order? check failed partial

The rest of the set reaches further: return rates, inventory stockouts, a quarterly target, return on ad spend by channel, a revenue forecast, and customer acquisition cost in the "Southeast". That last one is a good trap: storefront's regions are South, West, Midwest and Northeast, and there's no ad spend at all. A good judge should say so rather than quietly answering for the South, and in the re-score it did: Southeast shows up in the gap backlog as a missing dimensional value.

Judging them

Each question is answered for real. The Worker's /ai/coverage/check runs the same agent as the Ask window, with Publisher's MCP tools and skills and up to 14 tool turns, plus a coverage brief: find the names with get_context, state any interpretation, run the query, say which concept is absent and what the closest field is, and then write three sections, Recommended changes, Exit criteria, and a Verdict:

  • Answerable: every measure, grouping and filter is present.
  • Partly answerable: at least one is missing or only approximated.
  • Missing: the central measure or entity is absent.

An earlier version judged in bulk instead: a cheap classifier (Jev on Workers AI) scored each question's concepts against what get_context retrieved. It was fast, but I could consistently overturn its verdicts by re-running a question as a chat, which meant the heat map and the chat disagreed about the same model. Now the batch uses the same agent as the chat, so a re-score and a Re-run as chat judge a question the same way. Retrieval-only classification is still there as the fallback when Publisher's MCP endpoint is unreachable.

The score

The coverage score is the percentage of questions answerable, with a partial answer worth half:

score = round( (answerable + partial / 2) / judged × 100 )

Each score gets a grade chip so the number reads at a glance:

Score Grade Meaning
90+ Excellent Nearly every question is answerable from the model.
75–89 Good Most questions are answerable; a few gaps remain.
60–74 Fair Many questions work, but gaps are common.
40–59 Weak Large parts of the question set cannot be answered.
<40 Poor Most questions cannot be answered from the model.

I've kept the failed run next to the complete one, because the pair shows two things the UI already gets right and two it doesn't. A failed check is a distinct, visible state (a dashed red cell) rather than a silent "missing", and the score counts only what was judged. But a score over 9 of 25 questions still wears a green Good chip, and the legend calls the failures "waiting". A score with failures should say how much of the set it covers, and offer to retry just those questions. The same is true at the start of a run: one question in, the re-score briefly read 100, Excellent. And the −21 isn't really a change in the model. It's mostly the 16 questions that finally got judged. The delta should compare only questions judged in both runs.

The gap backlog

Add 25 questions grows the same set, and only the new questions are judged. New set starts fresh. Re-score these judges the same questions against the model as it is now. Runs that share a set are comparable, so a re-score shows a delta and a trend sparkline beside the score. The last five runs are kept under Recent runs.

06Reading a verdict

A score is only useful if you can see why each question landed where it did, argue with it, and hand the fix to someone.

This verdict is a good argument to have. The agent answered the question, correctly, from the model's own margin_rate measure. It marked it partial because one of the concepts Opus listed when it wrote the question, "product cost", isn't a named measure; products.cost is only a dimension. Its reasoning is careful, too: it notes that a naive products.cost.sum() through the join returns $831 for Shorts instead of the line-level cost, because Malloy's symmetric aggregation counts each product once, and recommends a total_cost measure on order_items so nobody reaches for the wrong one:

// Recommended change 1, from the agent's investigation
#(doc) Cost of goods sold: product cost summed per line item sold
# currency
# label="Cost of goods sold"
measure: total_cost is sum(products.cost)

So is it partial? As a question, no. As a model, there's a real gap: a cost-of-goods measure that the next question ("what did we spend on inventory last quarter?") will need. The verdict conflates the two because concepts are written up front, before anyone knows how the model expresses them. A sharper design would score the question on whether it was answered, and keep the concepts as diagnostics that feed the gap backlog on their own.

The re-score made that point for me. Same question, same model (the documentation patch had been reverted by then), same numbers to the decimal, and this time the verdict was answerable. The agent decided products.cost, already used per line inside gross_margin, was good enough for "product cost", and demoted the total_cost measure to an optional addition. Neither verdict is wrong, which is exactly the problem: a score should not move because the judge read the same evidence differently.

Argue with it, then hand it off

  • Re-run as chat. Reopens the question as a live conversation with the same agent, so you can push back ("margin_rate already answers this") and watch it reconsider. If it closes with a different verdict, Save verdict replaces the run's verdict and rescores the run.
  • Download. Exports the verdict as a markdown brief for a coding agent (or a PDF for a person): the question, the verdict and who judged it, the concepts with batch and chat evidence side by side, the recommended changes, the exit criteria, and the full investigation. The exit criteria are written to be checked by the receiving agent: a named measure exists and get_context returns it, a stated query returns stated numbers, and re-running the coverage check returns answerable.
  • Asked in chat. Questions asked in the Ask window land in the heat map on their own, in a separate row, judged from the chat's own answer. Coverage stops being a synthetic benchmark and starts reflecting what people actually wanted to know.

07Closing the loop on storefront

The two pages are designed as one loop: coverage finds what's missing, the dictionary helps describe or add it, and a re-score shows whether the number moved.

1 · Ask
Write or collect questions Generated sets, plus everything people ask in the Ask window.
2 · Judge
Answer each one for real An agent with Publisher's MCP tools and skills, closing with a verdict.
3 · Fix
Describe, then model Promote #(doc) drafts; hand modeling gaps to a coding agent.
4 · Re-score
Same questions, new model A delta and a trend line on the score.
↺ the gap backlog from step 4 is step 3's next to-do list

I got through the first three steps on storefront. To see the promotion land, I applied the promoted patch to the copy of storefront that Publisher serves from publisher_data/ (not to examples/), reloaded the package, took the screenshots below, and then reverted it.

The re-score I did run is not quite step 4. It judged the same questions against the original model, after I'd reverted the patch, so it measures two other things: the 16 questions the first run never judged, and how much the judge varies from run to run. On the 9 questions judged both times, 2 moved from partial to answerable with nothing changed (94 on those nine, against 83 the first time). The 16 newly judged questions score 44 on their own, and that is what pulls the total down to 62.

The real step 4, re-scoring with the documentation applied, is the next run. My hypothesis is that the documentation alone moves very little here. A #(doc) on products.cost makes it easier to find, but the gross margin and markup questions want a measure, and the retention, inventory, marketing and forecasting questions want data storefront doesn't have. That's the useful split the loop should make obvious: documentation fixes discoverability, the coding-agent handoff fixes modeling, and some gaps are data the business would have to bring in, which no model edit can fix.

08What the prototype taught me

Most of the read side came for free from what Publisher already serves. The friction was all on the write side, and in deciding what a verdict should mean.

Friction What happened Directional fix
No way to write a model file Dashboards, notebooks and (in Part 2) data apps have compile-first, hash-checked writes. Models don't, so promotion ends at a patch someone has to apply by hand. A PUT …/models/{path} with the same compile, hash and rollback rules, followed by a package reload
Columns can't carry a #(doc) without an experiment Describing a raw table column means rewriting its source into an include block and turning on ##! experimental.access_modifiers. It's the most common undocumented thing in a new model, and the hardest to annotate. A first-class way to annotate an inherited column (for example #(doc) inside extend by name), or graduate the experiment
Verdicts are graded against guessed concepts The gross margin question was answered correctly but scored partial, because a concept written before judging ("product cost") isn't a named measure. Score "was it answered?" separately from "which concepts were present?", and feed only the second into the gap backlog
Batch and chat used to disagree The cheap classifier and a chat re-run reached different verdicts on the same question, so the heat map couldn't be trusted. Done in the prototype: one agent judges both. The cost is time and tokens, so cheap classification should come back only as a pre-filter
Copy drifted from behavior The coverage page still says each question "is checked against what get_context actually retrieves", which described the old classifier, not the agent that judges now. Say who judged, per run and per verdict (the chips under the controls already do)
Agent judging is expensive and fragile Four concurrent Opus runs with a 14-turn budget each. On a thin balance, OpenRouter refused 16 of 25 checks outright. Retry failed questions on their own, back off on credit errors, show a cost estimate before a run, and label a score that covers 9 of 25 questions as partial
Verdicts move between runs Re-scoring the same 25 questions against the same model flipped 2 of the 9 earlier verdicts from partial to answerable. The re-score's −21 mixed that noise with 16 questions judged for the first time. Judge each question more than once and show agreement, compare deltas only over questions judged in both runs, and record the model's file hashes on every run so "same model" is checkable
State lives in the browser Drafts, runs and chat history are in localStorage, so a reviewer can't pick up a teammate's drafts, and coverage history isn't shared. Server-side drafts and runs per package, or, better, the same store the Credible app already uses for saved content

Concepts worth keeping

  • Views of the model, not just of the data. A dictionary, a content graph and a coverage map are all derived from the package. None needs authoring, and all of them improve when the model does.
  • AI drafts, people decide, the compiler checks. The same three-part shape as Part 2's promote flow: nothing AI-written reaches the model without a person accepting it and the package's compiler passing it.
  • Hedged drafts are a feature. "Appears to be" is a prompt for a reviewer. A confident description invented from a column name is worse than none, because get_context will rank on it.
  • Coverage is the discoverability metric agents need. Documentation percentage measures effort; question coverage measures outcome. It also gives eval work a zero-setup on-ramp: the eval-loop skills want verified goldens, and a coverage run is a cheap way to find which questions deserve one.

09Where it could go

Some directions I'd like to explore further, none of them validated with real users yet.

  • Coverage on a schedule, from real questions. Nightly re-scores of the questions people actually asked (in the Ask window, over MCP, in the Credible workspace), with the score's trend in the package header. A model change that drops the score is a regression, the same way a failing test is.
  • Gaps that open their own pull requests. The handoff brief already has recommended changes and exit criteria. Hand it to eval-improve, have it propose the smallest model edit, and have the next re-score accept or reject it, with a person approving the merge.
  • The dictionary as get_context's front end. The dictionary's pages and get_context's cards describe the same entities. One shared definition (doc, label, sample values, related content) would make what a person reads and what an agent retrieves the same thing.
  • A Model Health card. Fields nothing reads, joins that fan out, ambiguous names, measures with no dashboard, all computable from the same ontology the dictionary builds, and each one a draftable fix.
  • Inside the Credible workspace. Part 2's Library lists content; the dictionary explains the model under it. They belong on the same page, and the @-mention composer could mention dictionary entities directly.

What's in the tree

Like Parts 1 and 2, none of this is committed to the repo.

Piece State
Data Dictionary (packages/app/…/DictionaryPage/, src/ontology/) Working on any package, about 8.6k lines of TypeScript including the ontology builder. Read-only against Publisher; no server change.
Drafts, review and promotion Drafting, review, the diff and the compile check work end to end. Write to model waits on a model write endpoint; the patch applies with git apply.
Question Coverage (packages/app/…/CoveragePage/) Working, about 3k lines. Runs, verdicts and investigations are kept per browser (last five runs).
Ask window and chat (packages/app/…/chat/) Detached chat window with history, model picker and markdown answers; questions file into coverage.
AI Worker (packages/console-ai) Cloudflare Worker on TanStack AI and OpenRouter, about 1.5k lines: /ai/ask, /ai/dictionary/draft-docs, /ai/coverage/{questions,check,classify}, and chat titles. Loads Publisher's MCP tools and skills as its harness.

To reproduce the screenshots, run Publisher (bun run start from packages/server), the Worker (bun run dev from packages/console-ai, with an OPENROUTER_API_KEY in .dev.vars) and the Console on :5180, then node docs/unboxing/capture-data-dictionary.mjs [flow …]. The flows share one browser profile, because drafts and runs live in localStorage.
