Sidebar and chat: asking from where you are

Part 2 was a guess at the Credible app, made before I'd seen it. Since then I've had access, so this part starts from the real thing. I built a close copy of it, packages/credible-clone, and changed three things about how chat fits around content: where you find your chats, where a question asked from a dashboard is answered, and how a chat that outgrows the margin finds its way back.

Noah Mac · product + design engineering update · Oct 12, 2026
TL;DR
  • Chats get a home in the sidebar. A slim rail adds Chats beside My Workspace, Reports and Packages. It opens on hover and pins with ⌘B. The Chats page puts a standalone New chat next to every earlier chat, with search and filter chips for the package, report, or kind of content a chat is about. In the app today, the only list of past chats is the home page's Conversations section.
  • A question on a dashboard is answered beside the dashboard. Asking from the composer floating over a dashboard or notebook keeps you on the page. The answer streams into a column in the page's right margin, sharing its scroll, with each question pinned above its reply. The app today turns the same question into a full-page chat and moves the dashboard into a narrow panel beside it.
  • Every margin chat has a full page, and a way back. One button opens the chat in the Chats page, under a Started from Storefront overview banner. The banner returns to the dashboard with the chat still open beside it. The same origin is a filter in chat history: Report: Storefront overview.
  • The app's agent knows more than mine. The app's chat runs a dashboard's tiles before it answers and lists what it touched in a panel. The clone's agent only gets the report's title, and on a notebook it said so: "I couldn't open the Category review notebook's cells with these tools." The layout ideas here are worth more paired with the app's grounding than with mine.
  • It's a prototype. Fixture chats and in-memory threads; nothing survives a reload. The answers are live: Claude Opus 5.5 on OpenRouter, using Publisher's own MCP tools and skills against the bundled storefront package.

01Why start from the app

Part 2's last section said every next step depended on seeing the real Credible app. This is that step.

Part 2's demo workspace invented a Library, a For You page and an insight Studio without knowing what the app already did. That made it easy to build and hard to act on. So this time I started by cloning the app's shell from screenshots, close enough that a change could be judged against the original rather than against a different product. The clone is small, about 3,200 lines of TypeScript, and renders the same Publisher content the app does: dashboards and notebooks through the SDK, and an agent grounded by Publisher's MCP tools.

Three questions kept coming up while I used the app, and they shaped the clone:

Question Where it's answered
Where do I start a new chat, and where are my old ones? Section 03, the rail and the Chats page
If I'm reading a dashboard, can I ask about it without leaving it? Section 04, the margin chat
When a side conversation gets long, where does it go, and can I get back? Section 05, full page with a backlink

02The app today

A workspace home, a full-page agent, and content that opens in a panel beside it.

Asking from a dashboard

Two details from that pair shaped what I built. First, the breadcrumb on the chat reads My Workspace › Customers and acquisition, but that second crumb is the chat's title, which happens to match the dashboard's. Nothing on the page says the chat started from the dashboard; you have to infer it from the panel and the scope chip. Second, the dashboard's own Show chat button opens the chat that created the dashboard ("Additional dashboards"), not the later one that asked about it. So the app links content to the chat that made it, but not to the chats about it.

I didn't send any new questions in the app for this write-up. The report-started session above is one I'd already had, and its scope (the dashboard) and first message ("summarize this dashboard") show where it began. The app screenshots are from a window about 1,070 px wide, narrower than the clone's 1,440 px, so they're not quite to scale.

03A rail with a home for chats

The sidebar should answer "where do I start?" and "where was that chat?" from any page.

The Chats page

Search, then filter

An early version of the list put package and "1 dashboard" chips on every row. That was useful but noisy, so the chips moved into the search box. Focusing it opens a menu of filter templates, and picking one narrows the list with a chip that sits above it.

Compared with the app, the difference is less about the rail than about what's always in reach. The app's sidebar is contextual: its suggestions card offers Start a new chat from inside a chat and Ask across your workspace from home, which is a good prompt for someone new. But to reopen yesterday's chat, you go home and expand Conversations. The Chats page makes history a destination you can reach from anywhere, with the new-chat page as its first item.

04A chat in the margin

Asking about a dashboard shouldn't mean leaving it. The answer can live in the space the page wasn't using.

AskFrom the floating composer on a dashboard or notebook
→
Answer in the marginThe page widens and a chat column docks on its right
→
Follow upA composer returns under the thread once the reply lands
→
Open full pageWhen it outgrows the margin (section 05)

The column is part of the page, not a drawer over it. It has no border or background of its own, and it sticks to the top of the scroll area exactly as tall as what's visible, so it stays put while the dashboard scrolls beside it. The page's maximum width grows from 1,400 to 1,816 px to make room, which on a wide screen means the chat uses margin the dashboard was leaving empty anyway. The chat's id goes into the URL as ?chat=, which is how the full page links back (section 05).

Keeping the question in view

A margin is narrow, so a single answer can be several screens long, and a long answer read without its question loses its context. Each question pins to the top of the column while its reply scrolls under it, until the next question pushes it out.

On a notebook

That answer is the most useful screenshot in this part. The clone tells the agent only "the user is looking at the notebook Category review", and none of Publisher's MCP tools reads a dashboard's tiles or a notebook's prose. The app's chat ran the dashboard's tiles before it answered. Section 07 comes back to this, because a margin chat is a promise that the chat knows what's next to it.

05Full page, and the way back

A margin chat should be able to grow into a full chat without losing track of where it started.

The banner is the prototype's answer to the app's breadcrumb. Both sit at the top of the chat, but the breadcrumb says where the chat is filed (the workspace) and the banner says where it came from (a page you can return to). A chat that started from nothing in particular, like one from the home composer or New chat, gets no banner.

06Side by side

The two put chat and content in opposite places. The app makes the chat the page and the content a panel. The clone makes the content the page and the chat a margin.

Moment The app today The clone
Start a new chat The composer on home, or Start a new chat in a chat's suggestions card Chats in the rail opens New chat; the home composer works too
Find an earlier chat Home, Conversations, Show 7 more The Chats list on every chat page, with search and filters by package, report, or what it created
Ask from a dashboard Opens a full-page chat; the dashboard moves to a side panel Stays on the dashboard; the answer docks in the right margin
Know where a chat came from Implied by the panel and the scope chip A Started from … banner that links back, with the chat reopened beside the content
Chats about this content Show chat opens the chat that created it Filter history by Report
What the agent sees The artifact itself: it ran the dashboard's tiles The report's title and package only
What the agent touched A panel switcher of connections and draft files, plus scope history A folded list of tool calls in the reply
Persistence Server-side sessions In memory; gone on reload

Neither placement is right for every question. "Summarize this dashboard" or "build me another one" is work whose output is the chat, and the app's chat-first layout suits it. "Why is this number up?" while reading a dashboard is a side question, and the margin keeps the thing being asked about in full view. The clone's real claim is that the second kind should not have to become the first, and that when it does, the way back should be explicit.

07What the prototype taught me

The layout held up. Most of the friction is in what the chat knows, and in a narrow column.

Friction What happened Directional fix
The agent can't see the page The chat is told only the report's kind and title. On the notebook it said it couldn't open the cells, and answered from the model instead. Send the page with the question: the dashboard manifest from GET …/dashboards/{name}, its tile queries, the current givens, and for a notebook its prose. Part 3's Ask about this already sent the page as markdown.
Tables don't fit the margin Both answers' tables were clipped on the right (Margin, Order lines). Scroll tables inside their own box, tell the agent the column is narrow (the prompt already says "a few columns"), or offer Open full page on any wide table
Previews show raw markdown The new chat's row in history reads **The South brings in…. Strip formatting from previews, and preview the answer's first sentence rather than its last message
Titles are cut, not written A chat is titled with the first 60 characters of its question, so the header reads "…gross margin, and how". Title chats the way Part 3's Ask window did, with a short model-written title after the first reply
One chat per page at a time While a margin chat is open, the floating composer is hidden, so a second, unrelated question means closing the first. A New chat button in the column header, with earlier chats about this page one click away
A link that outlives its chat ?chat= makes a margin chat linkable, but threads live in memory, so after a reload the link opens "This chat doesn't exist". The app's server-side sessions. Nothing about the margin layout needs a different store.
Half the rail is placeholders Reports and Packages open stub pages; reports are reached from home. Give them the same list-and-filter treatment as Chats, or drop them until they have one

Concepts worth keeping

  • History is a place, not a section. A Chats page reachable from every screen, with New chat as its first item, answers both "where do I start?" and "where was that?".
  • Ask where you are, answer where you are. A side question gets a side answer, in space the page wasn't using, with the content still interactive beside it.
  • Every chat remembers its origin. Origin is a link back, a scope for follow-ups, and a filter in history. Those three uses of one fact are what make it worth recording.
  • The question stays on screen. In a narrow column, pinning each question above its answer, and starting each reply at its first line, does more for readability than any amount of formatting.

08Where it could go

The best version is probably both: the app's grounding and artifact panel, with the clone's margin and way back.

  • Margin first, panel when it grows. Start a question from a dashboard in its margin. If the chat starts producing things (a new view, a draft file, a second dashboard), offer to switch to the app's chat-first layout, with the dashboard as the panel's first artifact and a Started from banner above the chat.
  • Make the page part of the prompt. A margin chat should know which tiles are on screen, what filters are set, and which one the user last clicked. A drill on a tile could even become the question: "why is this bar taller?"
  • Chats about this, on the page. The app's Show chat knows which chat made a dashboard. Add the chats that asked about it, so a dashboard becomes a place where questions about it accumulate, for its author and for the next reader.
  • Suggestions from the content. The app's contextual suggestions card (Explain this dashboard, Find interesting insights) belongs in the margin too, as the column's empty state before the first question.
  • Save from the margin. Part 2's promote flow fits here naturally: a margin answer that matters becomes a saved insight, or a tile on the dashboard it was asked from.

What's in the tree

Like Parts 1 to 3, none of this is committed to the repo.

Piece State
App shell and home (packages/credible-clone) A close copy of the Credible app's workspace page on fixture data; about 3,200 lines of TypeScript in all. Dashboards and notebooks come live from the local Publisher.
Rail (src/components/Rail.tsx) Hover to expand, pin with ⌘B, light and dark mode. Reports and Packages are placeholders.
Chats page (src/pages/chats/) New chat, thread view, search, and filter chips by package, report, and what a chat created. Fixture history; new chats in memory.
Margin chat (src/components/ChatPanel.tsx, src/pages/ServedPages.tsx) Working on dashboards, notebooks and package pages, with pinned questions, stop, follow-ups, open full page, and the ?chat= link back.
Agent (server/agent.ts) TanStack AI in a Vite dev-server plugin at /ai/chat, Opus 5.5 on OpenRouter, with every Publisher MCP tool and the skills behind load_skill, malloy-analysis preloaded.

To reproduce the screenshots, run Publisher (bun run start from the repo root) and the clone (bun run dev from packages/credible-clone, with an OPENROUTER_API_KEY in .env.local), then node docs/unboxing/capture-sidebar-chat.mjs. It makes three live agent calls, so the answers will differ a little from run to run. The app screenshots were taken by hand in my personal workspace.
